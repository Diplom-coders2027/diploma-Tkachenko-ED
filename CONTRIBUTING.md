# Как работать с проектом и сдавать задания (Contributing Guide)

Привет! Этот репозиторий — твой выпускной дипломный проект. 

Здесь мы учимся работать по правилам взрослой коммерческой разработки. Правила простые, понятные и помогут тебе не потерять код и легко сдать проект.

---

## 🛑 1. Главное правило: не трогаем `main` напрямую

Ветка **`main`** — это чистовик твоего проекта. Там лежит только проверенная и рабочая версия.

- **Прямой пуш в `main` заблокирован:** если ты попробуешь сделать `git push origin main`, GitHub выдаст ошибку.
- Весь новый код попадает в `main` **только через Pull Request (PR)** после того, как преподаватель проверит работу и нажмет **Approve**.

---

## 🌿 2. Как создавать и называть ветки

Каждую задачу или этап делаем в отдельной ветке. Мы используем всего 3 типа веток:

| Ветка | Для чего | Пример названия |
| :--- | :--- | :--- |
| `stage/...` | Сдача этапа проекта | `stage/1-architecture`, `stage/2-mvp` |
| `fix/...` | Исправление бага или замечания | `fix/user-login`, `fix/db-connection` |
| `docs/...` | Документация, текст записки, схемы | `docs/chapter-1`, `docs/database-schema` |

### Как переключиться в новую ветку (команды в терминале):
```bash
# 1. Всегда обновляем main перед началом
git checkout main
git pull

# 2. Создаем новую ветку и сразу переходим в неё
git checkout -b stage/1-mvp
```

---

## 💬 3. Как подписывать коммиты

Сообщение коммита должно четко говорить, что ты сделал. Никаких «коммит», «asdf» или «поправил».

Используем всего 3 основных префикса:

- `feat: ...` — добавил новую функцию в код  
  *(Пример: `feat: добавлен эндпоинт регистрации пользователей`)*
- `fix: ...` — исправил ошибку или баг  
  *(Пример: `fix: исправлена ошибка валидации email`)*
- `docs: ...` — написал текст, добавил диаграмму или обновил README  
  *(Пример: `docs: добавлена схема таблиц базы данных в docs/`)*

> 💡 **Совет:** Если просто обновляешь зависимости или конфиг линтера, можно использовать префикс `chore:` *(например: `chore: добавлен Dockerfile`)*.

## 🚀 4. Шпаргалка: цикл сдачи этапа от А до Я

Весь процесс сдачи состоит из 5 понятных шагов:

### Шаг 1. Создай задачу (Issue)
1. В репозитории нажми вкладку **Issues** $\rightarrow$ зеленую кнопку **New issue**.
2. Выбери шаблон **«Сдача этапа проекта»**.
3. Заполни название (например, `Этап 1: Проектирование архитектуры`) и нажми **Submit new issue**. Запомни номер задачи (например, `#1`).

### Шаг 2. Напиши код в своей ветке
Создай ветку и спокойно работай:
```bash
git checkout -b stage/1-architecture
# ...пишешь код или документацию...
git add .
git commit -m "feat: реализована базовая модель данных"
git push -u origin stage/1-architecture
```

### Шаг 3. Открой Pull Request на проверку
1. Зайди на GitHub — появится желтая плашка с твоей веткой и кнопкой **Compare & pull request** (нажми её).
2. Заголовок сделай понятным: `[Этап 1]: Проектирование архитектуры`.
3. В описании PR укажи номер своей задачи: `Closes #1` (тогда при слиянии задача закроется автоматически).
4. В правой колонке в блоке **Reviewers** выбери своего преподавателя.

### Шаг 4. Правки и код-ревью
- Преподаватель посмотрит код и оставит замечания к строчкам.
- **Не создавай новый Pull Request!** 
- Просто исправь код на компьютере, сделай коммит и отправь в ту же ветку:
  ```bash
  git add .
  git commit -m "fix: исправлены замечания по структуре БД"
  git push
  ```
  Твой открытый Pull Request на GitHub обновится сам!

### Шаг 5. Слияние (Merge)
Когда преподаватель поставит зеленую галочку **Approved**:
1. Нажми кнопку **Merge pull request** (или **Squash and merge**).
2. Нажми **Delete branch** (чтобы не копить старые ветки).
3. Переключись на компьютере обратно на `main` и подтяни изменения:
   ```bash
   git checkout main
   git pull
   ```

Поздравляем, этап сдан! 🎉
