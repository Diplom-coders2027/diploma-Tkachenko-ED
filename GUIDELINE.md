# Руководство по выполнению выпускного проекта (Guideline)

Данный документ — это подробное практическое руководство по организации работы над дипломным проектом. Здесь описан весь цикл: от первого клонирования репозитория до финальной сдачи и защиты.

Процесс выстроен по стандартам реальной коммерческой разработки. Следование этим правилам сэкономит ваше время, предотвратит потерю кода и сформирует навыки, необходимые для работы в IT-компаниях.

---

## 1. Начало работы: создание и клонирование репозитория

### Шаг 1.1. Создание своего репозитория из шаблона
1. Откройте страницу репозитория-шаблона в браузере: `https://github.com/Diplom-coders2027/TEMPLATE_REPOSITORY`.
2. В правом верхнем углу нажмите зеленую кнопку **Use this template** и выберите **Create a new repository**.
3. В поле **Owner** убедитесь, что выбрана организация `Diplom-coders2027`.
4. В поле **Repository name** укажите имя по единому стандарту:
   `diploma-<фамилия>-<инициалы>`  
   *(Пример: `diploma-ivanov-ii` или `diploma-petrov-as`)*.
5. Выберите видимость: **Public**.
6. Нажмите **Create repository**.

### Шаг 1.2. Клонирование на свой компьютер
Откройте терминал (Git Bash, терминал в VS Code, PowerShell или терминал macOS/Linux) и выполните команды:

```bash
git clone https://github.com/Diplom-coders2027/<ИМЯ_ВАШЕГО_РЕПОЗИТОРИЯ>.git
cd <ИМЯ_ВАШЕГО_РЕПОЗИТОРИЯ>
```

### Шаг 1.3. Первоначальное заполнение паспорта
1. Откройте файл `README.md` в корне проекта.
2. В таблице паспорта проекта укажите тему работы, ваше ФИО, курс (3 или 5), номер группы и ФИО преподавателя.
3. Сохраните изменения.

## 2. Структура проекта: правила размещения файлов

Каждый файл в репозитории должен находиться строго на своем месте:

- `src/` — исходный код разрабатываемого приложения. Сюда помещаются модули, сервисы, тесты, конфигурационные файлы сборки (package.json, pyproject.toml, go.mod и т.д.).
- `docs/` — пояснительная записка, исходники схем и диаграмм (PlantUML, Mermaid, draw.io), файлы презентации. Требования к оформлению записки описаны в `docs/README.md`.
- `.env.example` — образец конфигурационных переменных. Если вы добавляете новую переменную окружения (например, порт или имя базы), обязательно добавьте ее название в этот файл.
- `.gitignore` — файл исключений. Никогда не удаляйте и не отключайте его. Он автоматически защищает репозиторий от попадания тяжелых библиотек (`node_modules/`, `venv/`), кэшей и временных файлов операционных систем.

## 3. Модель ветвления и защита ветки main

### Почему ветка main защищена
Ветка `main` — это официальный чистовик вашего проекта. Настройки безопасности GitHub физически блокируют прямой пуш в `main`. Попытка выполнить команду `git push origin main` завершится ошибкой.

Любой код и любая документация попадают в `main` только через Pull Request после проверки преподавателем.

### Именование веток
Для работы используются три типа веток:
- `stage/<номер>-<название>` — ветка для выполнения контрольного этапа (например, `stage/1-architecture`, `stage/2-mvp`).
- `fix/<название>` — ветка для исправления ошибок или доработок по замечаниям (например, `fix/db-connection`).
- `docs/<название>` — ветка для написания текста пояснительной записки или диаграмм (например, `docs/chapter-1`).

## 4. Пошаговый цикл сдачи этапа

Работа над каждым этапом проекта строится по строгому 5-шаговому циклу.

### Шаг 1. Фиксация задачи (Issue)
Перед тем как писать код, зафиксируйте объем работ на GitHub:
1. Перейдите во вкладку **Issues** вашего репозитория и нажмите **New issue**.
2. Выберите шаблон **Сдача этапа проекта**.
3. Укажите название этапа, дедлайн и список задач, которые планируете реализовать.
4. Нажмите **Submit new issue**. Обратите внимание на номер созданной задачи (например, `#1`).

### Шаг 2. Создание ветки и написание кода
Перед началом работы обязательно синхронизируйте локальную ветку `main` с сервером:

```bash
git checkout main
git pull origin main
```

Создайте новую ветку под этап и переключитесь в нее:

```bash
git checkout -b stage/1-architecture
```

Выполняйте работу и фиксируйте прогресс понятными коммитами. Рекомендуется делать коммиты регулярно, а не один огромный коммит в конце месяца.

Правила оформления сообщений коммитов:
- `feat: описание` — если добавлена новая функциональность в коде.
- `fix: описание` — если исправлена ошибка или баг.
- `docs: описание` — если добавлены тексты, схемы или описание в docs.
- `chore: описание` — служебные изменения (обновление зависимостей, конфигов).

Пример отправки коммитов на GitHub:

```bash
git add .
git commit -m "feat: реализована базовая модель данных пользователя"
git push -u origin stage/1-architecture
```

### Шаг 3. Самопроверка перед сдачей
Перед тем как открывать Pull Request, выполните три обязательные проверки:
1. Проект запускается локально без ошибок (командой из раздела быстрого старта в README.md).
2. В файлах отсутствуют секреты (пароли от БД, API-ключи). Все секреты должны быть в локальном `.env`, а в репозиторий отправляется только обновленный `.env.example`.
3. Запущены линтеры и тесты (при их наличии в проекте).

### Шаг 4. Открытие Pull Request (PR)
1. Откройте ваш репозиторий на GitHub.
2. В появившейся плашке нажмите **Compare & pull request** (или перейдите во вкладку **Pull requests** -> **New pull request**).
3. Проверьте направление слияния:
   - `base: main` <- `compare: stage/1-architecture`.
4. Заголовок PR сделайте четким: `[Этап 1]: Архитектура и базовая модель данных`.
5. Заполните шаблон Pull Request (он загрузится автоматически):
   - В строке связи с задачей напишите `Closes #1` (укажите номер вашего Issue из Шага 1).
   - Опишите кратко, что сделано по коду и по документации.
   - Отметьте чек-лист самопроверки.
6. В правой колонке в блоке **Reviewers** выберите вашего преподавателя.
7. Нажмите **Create pull request**.

### Шаг 5. Прохождение код-ревью и доработка замечаний
Преподаватель проверит ваш PR и оставит комментарии к конкретным строкам кода или текста записки.

**Главное правило работы с замечаниями:**
Никогда не закрывайте текущий Pull Request и не создавайте новый для исправлений.
Все доработки вносятся в ту же самую ветку:

1. Откройте проект на компьютере (убедитесь, что находитесь в ветке этапа).
2. Исправьте замечания в файлах.
3. Зафиксируйте и отправьте изменения:
   ```bash
   git add .
   git commit -m "fix: исправлены типы полей модели по замечаниям"
   git push
   ```
4. GitHub автоматически добавит новые коммиты в уже открытый Pull Request.
5. Напишите ответ преподавателю в комментариях на GitHub и нажмите **Resolve conversation**.

### Шаг 6. Слияние в main
Когда преподаватель проверит правки и поставит статус **Approved**:
1. На странице PR нажмите кнопку **Merge pull request** (рекомендуется **Squash and merge** для объединения мелких правок в один красивый коммит).
2. Нажмите **Delete branch**, чтобы удалить ветку этапа из удаленного репозитория.
3. Вернитесь в терминал на компьютере, переключитесь на `main` и подтяните изменения:
   ```bash
   git checkout main
   git pull origin main
   ```
4. Этап официально сдан. Связанная задача в Issues закроется автоматически.

## 5. Типовые нештатные ситуации и их решение

### Ситуация 1. Ошибка при попытке пуша в main
Симптом: В терминале сообщение `remote: - Changes must be made through a pull request`.  
Причина: Вы забыли создать ветку и сделали коммит прямо в `main`.  
Решение:
1. Не паниковать. Ваш локальный коммит никуда не пропал.
2. Создайте из текущего состояния новую ветку:
   ```bash
   git branch stage/1-temp
   ```
3. Откатите локальный `main` к состоянию сервера:
   ```bash
   git reset --hard origin/main
   ```
4. Переключитесь в созданную ветку и продолжайте работу:
   ```bash
   git checkout stage/1-temp
   git push -u origin stage/1-temp
   ```

### Ситуация 2. В коммит случайно попал секрет или тяжелый файл
Причина: Файл был добавлен до настройки `.gitignore` или добавлен принудительно.  
Решение:
1. Удалите файл из отслеживания Git, но сохраните его на диске:
   ```bash
   git rm --cached <путь_к_файлу>
   ```
2. Убедитесь, что путь к файлу записан в `.gitignore`.
3. Сделайте коммит:
   ```bash
   git commit -m "chore: убрать служебный файл из индекса"
   git push
   ```

### Ситуация 3. Возникли вопросы или технический тупик во время разработки
Если код не работает, библиотека не ставится или вы не уверены в архитектурном выборе:
1. Не пишите в личные сообщения преподавателю короткие фразы без контекста ("у меня ошибка, посмотрите").
2. Откройте в репозитории вкладку **Issues** -> **New issue** -> шаблон **Вопрос / Проблема / Баг**.
3. Заполните форму:
   - В чем суть проблемы;
   - Ссылка на ветку и конкретную строку кода;
   - Что вы уже пробовали сделать и какие результаты получили;
   - Какие варианты решения вы видите.
4. Преподаватель ответит прямо в задаче с указанием на причину ошибки.

## 6. Краткая памятка основных команд Git

```bash
# Проверка текущего статуса (какие файлы изменены)
git status

# Переключение на основную ветку и получение свежих изменений
git checkout main
git pull origin main

# Создание новой ветки и переход в нее
git checkout -b <имя_ветки>

# Добавление всех измененных файлов в индекс
git add .

# Создание коммита с понятным описанием
git commit -m "feat: краткое описание изменений"

# Отправка ветки на GitHub (первый раз)
git push -u origin <имя_ветки>

# Отправка последующих коммитов в ту же ветку
git push
```
